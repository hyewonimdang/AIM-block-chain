## 1. 백엔드 vs 프론트엔드: 흥미·몰입 비교

**이 프로젝트의 데이터로는 비교할 수 없다.** 프론트엔드 기록이 0건이다.

대신 백엔드 쪽 절대값만 보면:
- 흥미도는 5건 중 4건이 4, 1건이 3이다. 1~2(낮음)는 없었다.
- 몰입도는 4, 4, 4, 3, 3. 뒤로 갈수록 낮아졌다. 같은 날 연속 작업이었으므로 피로 효과일 수도, 화면 위주 작업(4·5단계)이 코드 읽기보다 몰입이 덜했을 수도 있다.
- 추가 학습 의향은 평균 3.5~4.0. "더 하고 싶다" 쪽이지만 강하지는 않다.

**[판단 필요]** 핵심 질문 1 "백엔드 관심은 적성인가 호기심인가" 는 이 데이터만으로 답이 나오지 않는다. 판단에 쓸 수 있는 간접 근거는 두 가지다.
- 긍정 쪽: 흥미도가 전 단계에서 3 이상이었고, 3단계에서 측정 방법을 두 번 틀리고도 세 번째를 시도했다. 추가 학습 의향이 5단계에서 4다.
- 유보 쪽: 2단계 노트에 "직접 짜기엔 아직 멀다", 3주차 확신도 메모에 "더 깊이 파고들면 많이 어려울 수 있겠다" 고 적었다. 흥미는 있으나 자신감은 낮다.
- 비교 기준으로 쓸 프론트엔드 데이터가 없으므로, 본인의 기존 프론트엔드 경험에서 느낀 흥미·몰입을 같은 1~5 척도로 떠올려 견주어야 한다. 이 비교는 같은 조건의 측정이 아니라는 점을 보고서에 명시해야 한다.

→ 내 판단: 블록을 기반으로 코드를 읽고 실험해 가는 과정은 재미있었지만, 처음 접하는 분야라 막막한 기분도 컸다.
현재로서는 적성이라기보다 호기심에 가깝다고 본다. 적성이라고 말하려면 직접 구현까지 해 봐야 한다.
프론트엔드는 이전 포트폴리오 활동이 이 프로젝트의 화면 작업보다 훨씬 심화된 내용이어서 비교 기준으로 더 적절하다고 판단해 따로 측정하지 않았다.

## 2. 블록체인 자료구조 vs 분산 네트워크 (핵심 질문 2)

| | 블록체인 자료구조 (1~4) | 분산 네트워크 (5) |
|---|---|---|
| 흥미도 | 3.75 (3~4) | 4 |
| 몰입도 | 3.75 (3~4) | 3 |
| 추가 학습 의향 | 3.5 (3~4) | 4 |

숫자만 보면 분산 네트워크가 흥미도와 학습 의향에서 0.25~0.5 높고, 몰입도는 0.75 낮다. 그러나 **1건 대 4건의 비교이고 차이가 척도 한 칸 미만**이라 통계적으로 의미를 부여할 수 없다.

숫자보다 더 직접적인 근거는 5단계 소감이다. 소감 초안은 "더 흥미로웠다 / 더 귀찮았다" 두 갈래로 제시됐고, 본인이 고른 것은:

> "노드가 서로를 찾는 문제가 블록 자체보다 흥미로웠다."

이것은 점수가 아니라 선택이므로, 핵심 질문 2에 대한 가장 직접적인 자기 보고다.

노트에서도 방향이 일관된다.
- 1~4단계 노트는 "이해됐다", "원칙을 들으니 이해됐다" 처럼 **이해 확인** 중심이다.
- 5단계 노트는 "내 상태뿐 아니라 내가 누구를 아는가도 상태다", "포크는 고장이 아니라 자연스러운 결과" 처럼 **개념을 자기 말로 재진술** 하는 문장이 나온다.

**데이터가 말하는 만큼의 결론**: 흥미의 방향은 "블록체인 자체" 보다 "분산 구조(P2P)" 쪽으로 기울어 있다. 초기 가설("분산 시스템 구조에 흥미")과 일치한다. 다만 근거가 1건의 점수와 1줄의 소감이므로 "기울어 있다" 이상으로 말할 수 없다.

**[판단 필요]**
- 5단계 몰입도가 3으로 가장 낮았다. "흥미는 높은데 몰입은 낮다" 를 어떻게 읽을 것인가. (a) 피어 소실·포크 실패 등 실험이 두 번 꼬여서 흐름이 끊긴 탓, (b) 화면 클릭 위주라 손이 덜 간 탓, (c) 실제로 몰입이 덜 되는 영역. 본인만 구분할 수 있다.
- 분산 네트워크를 25분, 실험 2개로 본 것이 "흥미" 를 판단하기에 충분한 노출이었는가. 건너뛴 연습(악의적 노드, 작업량 비교, 노드 100개)을 추가로 해 봐야 확신할 수 있는지 판단할 것.

→ 내 판단: (a)~(c) 중 무엇이라기보다는, AI 가이드를 따라 하는 방식 자체가 원인이었다고 본다.
직접 설계하지 않고 순서대로 클릭하다 보니 몰입이라기보다 "따라 하는" 느낌이었고, 이해도 깊지 않았다고 스스로 느꼈다.
그래서 25분·실험 2개는 흥미의 방향을 보기엔 충분했지만 확신하기엔 부족하다. 건너뛴 연습(악의적 노드, 작업량 비교, 노드 100개)을
가이드 없이 직접 해 보는 것이 다음 검증으로 적절할 듯 하다.

## 3. 막힌 지점의 패턴과 시사하는 보완 역량

막힌 지점을 유형별로 묶으면:

| 유형 | 사례 | 단계 |
|---|---|---|
| 환경·도구 | PowerShell 에서 curl 이 동작하지 않음, `--` 옵션이 전달되지 않음, 서버가 꺼진 줄 모름, 재시작 방법 | 1, 4 |
| 측정·검증 방법 | 채굴 중 블로킹을 재려다 타이밍 방식·Start-Job 방식 모두 실패 | 3 |
| 상태·수명 이해 | 재시작한 노드가 피어 목록까지 잃는 것을 예상 못 함, 포크 실험에서 피어를 비우지 않음 | 5 |
| 코드 작성 | 검사 순서를 바꿀 위치를 못 찾음, findAllBroken 을 직접 짜지 못함 | 2 |
| 전체 그림 | 문제가 무엇을 묻는지, 시스템이 어떤 구조인지 처음에 감이 없었음 | 1 |

패턴:
1. **개념 이해에서 막힌 경우는 거의 없다.** 해시·연결·검증·작업증명·포크 모두 설명 후 노트에 자기 말로 정리됐다. 막힌 곳은 대부분 "개념을 확인하려고 실행하는 과정" 에 있었다.
2. **막힘의 대부분이 환경과 프로세스 수명에 관한 것이다.** 서버가 꺼졌는지, 재시작하면 무엇이 사라지는지, 요청이 실제로 언제 나갔는지. 프론트엔드에서는 브라우저가 이 부분을 대신 관리해 주기 때문에 겪지 않던 종류다.
3. **코드 작성 독립성이 낮다.** 2단계에서 구조(return → push)는 이해했으나 직접 작성하지 못했고 AI 코드를 참고했다. 1~5단계 전체에서 본인이 처음부터 작성한 코드는 없다.

시사하는 보완 역량 (데이터 기반):
- **Node.js 프로세스와 런타임 모델**: 메모리 수명, 이벤트 루프, 싱글 스레드 블로킹. 3-3·5-1 에서 직접 체감했고 노트에도 "프론트와 가장 다른 점" 이라고 적었다.
- **터미널·셸 숙련도**: PowerShell 과 Unix 계열 명령의 차이, 백그라운드 실행, 동시 요청 보내기.
- **실험 설계 능력**: "무엇을 재려면 어떻게 보내야 하는가" 를 먼저 생각하는 습관. 3단계에서 두 번 틀린 뒤 세 번째에 맞췄다.
- **백엔드 코드 작성 경험 자체**: 읽기는 되지만 쓰기는 안 된 상태. 이것이 "적성" 판단을 가장 크게 유보시키는 요인이다.

**[판단 필요]** 이 막힘들이 "배우면 되는 것" 인지 "성향에 안 맞는 것" 인지. 환경·도구 문제는 전자일 가능성이 높지만, 코드 작성을 시도조차 하지 않은 것(2단계, 그리고 전체)은 시간 부족 때문인지 회피인지 본인만 안다.

→ 내 판단: 환경·도구 문제는 배우면 되는 것이다.
코드 작성을 피한 것은 시간 부족도 직접적인 원인이기도 했지만, 시간이 있었어도 처음부터 짜는 것은 부담스러웠을 것 같다.
그래서 "배우면 되는 것" 으로 단정하지 않고, 직접 구현을 한 번 해 본 뒤 판단을 보류한다.

## 4. 진로 가설 확신도 추이

| 주차 | 확신도 | 계기 |
|---|---|---|
| 1 | 7 | 초기 가설: 분산 시스템 흥미 → 블록체인 백엔드 적합 |
| 2 | 4 | AI 반론 검증 + 채용공고 16건 분석 |
| 3 | 6 | 직접 구현·실험 후 |
| 4 | 7 | findings 를 읽은 뒤 최종 판단 |

2주차 하락은 "외부 정보(채용공고)" 에 의한 것이고, 3주차 반등은 "직접 경험" 에 의한 것이다. 3주차 메모는 반등의 성격을 분명히 한다.

> "흥미는 있었지만, 개념을 더 깊이 파고들면 많이 어려울 수 있겠다고 느꼈다. ... 현업에서 실제로 어떻게 쓰이는지, 기본 연습을 넘어 심화로 갈 때 어떻게 공부해야 하는지를 더 알아봐야 확신할 수 있을 것 같다."

즉 6은 "적합하다는 확신" 이 아니라 "해 보니 싫지는 않다 + 아직 모르는 게 많다" 의 합이다. 확신도가 올랐지만 메모는 유보적이라는 점이 이 데이터의 핵심이다.

**[판단 필요]** 4주차 확신도는 이 문서를 읽은 뒤 입력한다. 고려할 것:
- 수정 가설("기획·프론트엔드 역량을 바탕으로 블록체인 서비스 분야에 적합, 백엔드 적합성은 경험으로 확인 필요") 중 "경험으로 확인" 이 이번에 어느 정도 이루어졌는가.
- 이번 경험이 가리키는 방향이 "블록체인 백엔드" 인지 "분산 시스템 백엔드(블록체인에 한정되지 않는)" 인지. 2절의 소감은 후자 쪽 해석도 가능하다.

→ 내 판단: "경험으로 확인" 은 절반만 이루어진 것 같다. 코드를 읽고 실험하며 블록체인이 어떤 구조로 돌아가는지는 대략 파악했지만,
직접 구현하는 경험은 하지 못해 백엔드 적합성 자체는 아직 확인되지 않았다.
방향은 "블록체인 백엔드" 보다 "분산 시스템 백엔드" 쪽에 가깝다. 블록 자료구조보다 노드가 서로를 찾고 맞추는 문제에 더 끌렸고,
그 문제는 블록체인에 한정된 것이 아닌 것 같다.
그래서 4주차 확신도는 7로 둔다. 1주차와 같은 숫자지만 근거가 다르다. 1주차는 "분산 시스템이 흥미로울 것 같다" 는 예상이었고, 4주차는 실제로 해 본 뒤 "분산 쪽이 더 끌렸다" 는 경험이다.

## 5. 정리: 데이터가 말하는 것과 말하지 않는 것

말하는 것:
- 백엔드 작업 5건 모두 흥미도 3 이상. 싫어하는 영역은 아니다.
- 흥미의 방향은 블록 자료구조보다 분산 네트워크 쪽으로 기울어 있다. (1건 + 소감 1줄 기준)
- 막힘은 개념이 아니라 환경·프로세스·측정 방법에서 왔다.
- 코드를 직접 쓰는 단계까지는 가지 못했다.

말하지 않는 것:
- 프론트엔드와의 비교 (측정 안 함)
- 장기간 지속되는 흥미인지 (하루치 데이터)
- 직접 구현할 때의 적성 (AI 구현 코드를 읽고 실험한 데이터)
